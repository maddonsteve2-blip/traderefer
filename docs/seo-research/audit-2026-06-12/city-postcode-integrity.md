# City / Postcode Data Integrity Audit — 2026-06-12

Scope: `/local/[state]/[city]/[suburb-postcode]/[trade]/[job]` URL tree on traderefer.au.
Trigger: GSC exports showing 308-redirecting wrong-postcode slugs (`kallangur-1269`, `hornsby-2000`)
and bogus city segments (`/local/qld/brookside/`, `/local/wa/cannington/`, `/local/nsw/dee-why/`, ...).

Everything below was verified against the repo at `master` (df208e80), the Neon production DB,
the live site (curl, 2026-06-12), and the sitemap snapshots `C:\Users\61479\sm-suburbs.xml` / `sm-trades.xml`.

---

## TL;DR

1. **Postcodes (active, getting worse):** the suburb→postcode map in `apps/web/lib/postcodes.ts`
   is auto-generated by `scripts/regenerate_postcodes.js` from a poisoned reference table plus a
   "first 4-digit number in any business address" fallback. The 2026-05-25 regeneration (commit
   `cfa6fa98`) silently **changed 167 suburbs' canonical postcodes**, fixing some (kallangur
   1269→4503) but **regressing others** (hornsby 2077→**2000**, ryde 2112→**2122**). Because every
   `/local` page 308s non-canonical slugs to the map value, the site is **live right now redirecting
   the CORRECT URLs to WRONG ones**:
   - `…/hornsby-2077` → 308 → `…/hornsby-2000` (verified live)
   - `…/ryde-2112` → 308 → `…/ryde-2122` (verified live)
   **30 suburbs** have confidently-wrong postcodes in the current map → **461 live sitemap URLs**
   carry a wrong postcode as their canonical, and every previously-indexed correct variant now
   308s into them. Each future regeneration re-rolls the dice (redirect ping-pong across deploys).

2. **City segment (mostly historical, one validation gap):** the city segment is **never validated
   anywhere** — sitemaps mint it raw from `LOWER(REPLACE(businesses.city,' ','-'))`, and the page
   components just query `LOWER(city) = <segment>`. Any business row with `city='Brookside'`
   mints an entire URL subtree. A DB cleanup around 2026-03-21/22 normalized `businesses.city`
   to `locations_reference` parent cities (0 mismatches remain for ref-known suburbs), but:
   - the **483-entry static redirect file** (`location-redirects.ts`, exported 2026-03-22) only
     covers cloverdale/cockburn/cottesloe/perth/rockingham/liverpool paths — **none of the GSC
     bogus cities (brookside, cannington, dee-why, epping, glebe) have redirects**; those URLs
     return **200 + noindex + self-referencing canonical** (crawl-budget waste, verified live);
   - one junk city survives in the DB: **`qld/douglas`** — 26 active businesses with
     city='Douglas' AND suburb='Douglas' whose addresses are actually in **Kirwan (Townsville
     4817)** and **Port Douglas/Craiglie (4877)**; the map says douglas=4354 (a Toowoomba-region
     locality). `…/qld/douglas/douglas-4354` is **200 + index,follow** (verified live) — an
     indexable page for a fake locality with a wrong postcode.

## 1. How the URL tree is minted (data flow)

```
businesses.state ──→ /local/[state]                 (raw, lowercased)
businesses.city ───→ /local/[state]/[city]          (raw, LOWER(REPLACE(' ','-')), NO validation)
businesses.suburb ─→ /local/.../[suburb-postcode]   (slug + postcode from SUBURB_POSTCODES map,
                                                     fallback: first 4-digit token in address)
```

- **Sitemaps** (`apps/web/app/sitemaps/[sitemap]/route.ts`):
  - `suburbsSitemap()` / `tradesSitemap()` GROUP BY raw `LOWER(REPLACE(city,' ','-'))` — line 174/204.
    The city segment is whatever string sits in `businesses.city`.
  - The suburb segment goes through `sitemapSuburbSegment()` → `getCanonicalSuburbSlug()`; if the
    map has no entry, `postcodeFromAddress()` (line 79-83) grabs the **first** state-range-valid
    4-digit token from `MAX(address)` of the group — street numbers and head-office postcodes match.
- **Pages** (`[suburb]/page.tsx` line 162-167, `[trade]/page.tsx` line 225-230, `[job]/page.tsx`
  line 142-147): `permanentRedirect()` (308) whenever the URL's suburb slug ≠
  `getCanonicalSuburbSlug(suburb, state)`. **The map value always wins** — so a wrong map value
  redirects the correct URL to the wrong one.
- **City pages** (`[city]/page.tsx`): `notFound()` only when no suburbs exist for that (state, city).
  Suburb/trade pages under a bogus city never 404 — they render thin with
  `robots: index: stats.total >= 2 || categories >= 2`, i.e. **a bogus city with ≥2 businesses is
  indexable** (the qld/douglas case).
- **Middleware** (`apps/web/middleware.ts` line 42-62): 301s for exact/base-path matches in the
  static `LOCATION_REDIRECTS` map (483 entries, frozen 2026-03-22; DB table `location_redirects`
  has the same 483 rows, latest row 2026-03-17).

**The city segment is never checked against any whitelist at any layer.** `lib/locations.ts`
(`LOCATIONS`) is a vestigial Geelong-only structure that nothing in the `/local` tree uses.

## 2. Root cause of the wrong postcodes

`scripts/regenerate_postcodes.js` builds `SUBURB_POSTCODES` with this priority:

1. `locations_reference.postcode` — **if it passes the state range check**;
2. else: the **first** `\b\d{4}\b` token in **one arbitrary business address** for that
   (suburb, state) — first row wins, no modal/majority logic, no "token must be at the end of the
   address" anchor.

Three independent poisons:

- **`locations_reference` contains PO Box / LVR postcodes.** 163 rows are state-invalid
  (93 NSW, 26 WA, 22 SA, 12 ACT, 7 VIC, 2 NT, 1 QLD), e.g. Hornsby NSW = "1630", Epping NSW =
  "1710", Ryde = "1680", Sutherland = "1499", Strathfield = "1819". These come from a dataset
  that lists *post-office-box* ranges, not delivery postcodes. The script silently rejects them
  → falls to the address fallback → e.g. a Hornsby business with a Sydney-CBD office address
  ("… Sydney NSW 2000") minted `hornsby → 2000`.
- **`locations_reference` also contains state-VALID but wrong postcodes** that sail through the
  range check: Chatswood = "2057" (PO-box-only; delivery is 2067), and the dual-locality
  collisions — Epping NSW resolved to 2118 (Carlingford), Douglas QLD = 4354 (Toowoomba region,
  not Townsville's 4814).
- **The address fallback matches any 4-digit token** (`\b\d{4}\b`) that falls in the state range —
  street numbers ("2000 Pacific Hwy"), unit blocks, and head-office postcodes all qualify; the
  business row it samples is arbitrary (`DISTINCT ON … ORDER BY address DESC`).

  (map 2153, addresses 2620 — Queanbeyan's Crestwood, not Baulkham Hills), plus narrabundah, reid,

## 3. Root cause of the bogus cities

`businesses.city` is free-text from ingestion (Google-Places-derived locality guesses). Until the
March cleanup it contained shopping centres ("Brookside" — a mall in Mitchelton), wrong
neighbours ("Cannington" for Maddington businesses, "Dee Why" for Brookvale), and suburbs-as-cities
("Epping", "Glebe"). Because **nothing validates the city segment**, each such value minted a whole
indexable subtree in the sitemaps, which Google crawled.

Current DB state (verified today):

- 105 distinct active (state, city) pairs; every one of them now matches `locations_reference`
  (81 parent cities + standalone towns); `businesses.city` vs ref `parent_city_slug` mismatches
  for ref-known suburbs: **0 of 30,864**.
- 87 of the 105 city values also exist as a suburb value (mostly legit: city=sydney/suburb=sydney
  pattern; 2,723 businesses have `city = suburb`).
- **Surviving junk: `qld/douglas`** (26 businesses, city=suburb='Douglas', addresses in
  Kirwan/Townsville and Port Douglas/Craiglie). The "standalone_town" type in
  `locations_reference` let it pass: there is a real (tiny) Douglas QLD 4354 near Crows Nest,
  so the textual check succeeds while the semantics are wrong.
  Similar but benign-ish: burpengary/morayfield/caboolture (Moreton Bay — addresses match),
  rosebud (Mornington Peninsula), picton, agnes-water, willowbank — real towns, businesses really
  there; their only sin is being modeled as "cities" (city==suburb single-suburb subtrees).
- The legacy GSC URLs under brookside / cannington / dee-why / epping / glebe city segments have
  **no redirect coverage** (the 483-entry table predates them or never included them). They are
  now 200 + `noindex,follow` + **self-referencing canonical** thin pages (suburb and trade level)
  or 404 (city level). Verified live:
  - `/local/qld/brookside/mitchelton-4053` → 200, noindex, canonical = itself
  - `/local/wa/cannington/maddington-6109/plumbing` → 200, noindex, canonical = itself
  - `/local/qld/douglas/douglas-4354` → 200, **index,follow** ← the one actively bad page set

In the **current** sitemaps the city axis is nearly clean: 20 non-parent-city segments in
sm-suburbs (20 URLs) and 49 in sm-trades (178 URLs), almost all legitimate country towns; the
only data-wrong one is `qld/douglas` (12 URLs).

## 4. Recommended fix

### A. Make the postcode source of truth real (root fix)

1. **Stop deriving postcodes from business addresses.** Load the official postcode dataset
   (e.g. GNAF/Australia Post locality file, or the `australian-postcodes` open dataset) into
   `locations_reference` — replace the 163 state-invalid PO-Box rows and audit the state-valid
   ones (chatswood 2057-class errors) by joining on locality name + state.
2. **Fix `scripts/regenerate_postcodes.js`:**
   - drop the per-business address fallback entirely, or demote it to: *modal* postcode across
     all of the suburb's businesses, taking the **last** state-valid token of each address
     (AU formatted addresses end "Suburb ST 2077, Australia"), require ≥2 samples and >50%
     agreement — this exact heuristic found the 30 bad entries above;
   - **diff-guard:** print and require manual confirmation for any entry whose postcode *changes*
     from the committed map. 167 silent flips in one run is how this shipped.
3. **Immediate hotfix (before the dataset work):** patch the 30 confirmed-wrong entries in
   `apps/web/lib/postcodes.ts` (hornsby→2077, chatswood→2067, ryde→2112, epping→2121,
   north-sydney→2060, strathfield→2135, gladesville→2111, sutherland→2232, st-clair→2759,
   kingswood→2747, crows-nest→2065, woollahra→2025, canberra→2601, … full list in §2) and add a
   unit test asserting these anchor values so a regen can't silently revert them.
   Note: a few "mismatches" are mis-suburbed businesses rather than map errors (bossley-park
   2176 is correct; its businesses have Wetherill Park 2164 addresses) — verify each against the
   postal dataset, not just the address modal.

### B. Validate the city segment (close the open door)

4. **Whitelist at mint time:** in `apps/web/app/sitemaps/[sitemap]/route.ts`, join the
   city GROUP BY against `locations_reference` (parent cities + standalone towns) or an exported
   `CITY_WHITELIST` constant generated the same way `postcodes.ts` is; skip any group whose city
   isn't whitelisted (log to `fill_queue`-style table for triage instead).
5. **Validate at render time:** in `[city]/page.tsx`, `[suburb]/page.tsx`, `[trade]/page.tsx` —
   if the city segment isn't in the whitelist, look up the suburb's canonical parent city in a
   generated `SUBURB_TO_CITY` map (from `locations_reference.parent_city_slug`, same codegen
   pattern as `SUBURB_POSTCODES`) and `permanentRedirect()` to
   `/local/[state]/[canonical-city]/[canonical-suburb]/…`; if the suburb is unknown too,
   `notFound()`. This retires the frozen 483-entry `LOCATION_REDIRECTS` file: brookside,
   cannington, dee-why, epping, glebe and any future junk city all redirect generically, and the
   noindex+self-canonical zombie pages disappear. (Keep the middleware map for the
   suburb-moved-city cases it already encodes, or fold those into `SUBURB_TO_CITY` as well.)
6. **Canonical should not echo the request URL's city.** Today `generateMetadata` builds
   `canonicalUrl` from the raw `city` param — a duplicate subtree canonicalizes to itself.
   After (5) this matters less, but the canonical should be built from the resolved city.

### C. Data cleanup SQL

```sql
-- 1. Fix the Douglas mess (26 rows): re-derive suburb from address, re-parent city
UPDATE businesses SET suburb='Kirwan',  city='Townsville', updated_at=now()
 WHERE status='active' AND state ILIKE 'qld' AND city='Douglas' AND address ILIKE '%kirwan%';
UPDATE businesses SET suburb='Craiglie', city='Port Douglas', updated_at=now()
 WHERE status='active' AND state ILIKE 'qld' AND city='Douglas' AND address ILIKE '%craiglie%';
UPDATE businesses SET suburb='Port Douglas', city='Port Douglas', updated_at=now()
 WHERE status='active' AND state ILIKE 'qld' AND city='Douglas' AND address ILIKE '%port douglas%';
-- (Port Douglas needs a locations_reference standalone_town row, postcode 4877.)

-- 2. Replace PO-box postcodes in locations_reference from a proper dataset; interim flag:
UPDATE locations_reference SET is_active=false
 WHERE postcode ~ '^[0-9]{4}$' AND state_code='NSW' AND postcode::int < 2000;  -- 80 rows; repeat per state rules

-- 3. Re-export redirects after adding generic city-redirect support (or backfill rows for the
--    legacy GSC cities so the static file covers them until (5) ships):
INSERT INTO location_redirects (old_path, new_path)
SELECT '/local/qld/brookside/' || slug-paths…  -- generated from locations_reference parent mapping
```

### D. Ordering

1. Hotfix the 30 postcodes + anchor tests (stops the live wrong-direction 308s — biggest SEO harm).
2. Douglas cleanup SQL + sitemap city whitelist (kills the last indexable fake locality).
3. Generic city-segment redirect via `SUBURB_TO_CITY` codegen (retires zombie noindex pages).
4. Postal-dataset import + regenerate script rewrite + diff-guard (prevents recurrence).
